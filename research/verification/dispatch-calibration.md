# 固定预算与重复下令的局部校准

实验于2026-09-28（Asia/Shanghai）运行。未修改 `src/`、`tests/` 或 `src/main.ts`。实际结果、完整命令记录、逐时刻兵力账本、源文件SHA-256见 [dispatch-calibration.json](dispatch-calibration.json)。

直接读取 `src/main.ts` 中长录像场景的配置，仅覆盖 `aiEnabled:false`；使用原 `longMap`、seed731、30tick/s。SW起始200，W中立125；蓝生产13.7/s、中立7/s，5兵/批、16兵/s，速度80px/s。其他阵营存在但不行动。研究脚本调用现有GameEngine，没有另写战斗公式。

| 指标 | 仅tick0下令一次100% | 源队列清空后再次下令100% |
|---|---:|---:|
| W首次归蓝 | 90秒内未发生 | 15.733秒（tick472，剩1兵） |
| 20秒SW驻军 | 250 | 154 |
| 20秒W驻军/归属 | 48，中立 | 124，蓝 |
| 20秒累计发出 | 200（40批） | 320（64批） |
| 20秒已接受命令 | 1 | 2 |
| 20秒在途/未发预算 | 0 / 0 | 35 / 51 |
| 90秒累计发出 | 200 | 1432 |
| 90秒已接受命令 | 1 | 84 |
| 90秒SW / W | 250 / 中立125 | 1 / 蓝1301 |
| 逐tick守恒检查 | PASS，2702次 | PASS，2785次 |

两组首兵发射均0.333秒、首兵抵达2.300秒。第一条200兵预算均于12.500秒发完。重复假设在同一时刻以当时实际可用171兵建立第二个预算；第三次下令在23.200秒。20秒快照在tick600完成后、下一次下令检查前读取。

第二组规则严格是“已无该源队列且尚有实际可用兵力时，再提交一次固定预算命令”，即模拟重复手势；占领后仍按同规则向W增援直至90秒。后期频繁的小预算与W1301是这个实验规则的自然结果，不是原录像行为的主张。84次也不是原版用户实际操作次数。

单次预算失败的原因是出兵历时12.5秒，目标在被攻击期间持续恢复。200兵既要消耗初始125，也要消耗约12秒内新增的守兵，因此尾兵抵达后仍留下守军。之后SW回满250、W回满125，战场局部停止变化。增加驻军上限不会使已经结束的命令继续发兵。

录像L在16.5秒W仍灰，17秒已蓝。重复下令假设15.733秒占领，比该窗口早约0.77–1.27秒；比单次预算显著接近。但录像首帧SW是187且已经处于行动中，本实验从SW200、tick0指令开始；原片手势未完整可见，设施效果也未校准。因此不能将这一时间接近宣布为同输入重放通过，更不能说永久自动通道已被证明。可确认的是：**在本套校准参数下，一次200兵固定预算不足以复现该扩张；额外投入是待辨识的关键差异。** 原版可能使用重复手势、持续通道或其他预算策略，需要进一步输入证据。

复现（仓库根目录，Node26）：

```powershell
node research/verification/run-dispatch-calibration.mjs
```

运行器仅用Node内置TypeScript类型擦除在内存加载现有引擎和地图；参数脚本为 [dispatch-calibration.ts](dispatch-calibration.ts)。两种执行入口所得关键数字一致。每tick调用引擎的 `assertInvariants()`，另在起点和每次指令后检查；原始源文件在本次实验前后哈希一致。
